# 7. Train the ML Risk Model on Parameterized Distribution Profiles with Labels Independent of the Rule Engine

* Status: accepted
* Date: 2026-05-01
* Deciders: Tony

## Context and Problem Statement

The Risk Evaluator combines two scoring paths in an ensemble: a rule-based path (signal weights + boolean conditions, configured via policy) and an ML-based path (a Random Forest classifier consuming a 16-feature vector from the enriched event context). The two scores are blended at a configurable ratio (default 60% rules, 40% ML) to produce the final risk score.

The ensemble is only valuable if its two paths reach their conclusions through *independent reasoning*. If the ML model is trained on labels derived from rule-engine output — "the rules said DENY, label this event malicious" — the model learns to approximate the rule engine, and the ensemble degenerates into `0.6 × rules + 0.4 × rules_again`. The two paths agreeing then provides no extra signal because they were never independent in the first place.

Beyond avoiding that anti-pattern, NAAS faces a cold-start problem: the system runs on synthetic data generated by the Persona Simulator, with no production traffic to learn from. Training data must be bootstrapped from scratch.

How should the model be trained?

## Decision Drivers

* The ML path's score must be derived from reasoning genuinely independent of the rule path
* No production data exists, so training data must be synthesized
* The training process must be reproducible — re-running the bootstrap script must produce a model with materially equivalent behavior
* The training script must run quickly so it can be re-executed during development
* The data-generation process should encode IAM domain knowledge transparently so future maintainers can reason about what the model has learned
* The ML path's primary value is detecting correlated multi-signal patterns the linear rule engine cannot express

## Considered Options

* **Synthesize training data from parameterized distribution profiles, with labels derived from each profile's category** (chosen): hand-design a small number of benign and malicious archetypes, each parameterized as distributions over the 16 features; sample to produce a labeled dataset
* **Train on rule-engine output**: run the rule engine over a large set of synthetic events, use the resulting decisions as labels
* **Train on real production data**: not available — NAAS has no production traffic
* **Generate training data with an LLM** (e.g., prompt Claude to produce labeled event records)
* **Skip ML entirely, use only rule-based scoring**

## Decision Outcome

Chosen option: **Parameterized distribution profiles with labels derived from each profile's category.** Twelve profiles are defined: six benign archetypes (e.g., "FTE on corporate network during business hours", "contractor on VPN during business hours") and six attack patterns (e.g., "low-and-slow probe with moderate signals across the board", "credential-stuffing burst with high failed-login counts and impossible travel"). Each profile specifies the mean and standard deviation for each continuous feature and the probability of `True` for each boolean feature. A standalone bootstrap script (`scripts/train_bootstrap_model.py`) samples each profile to produce a labeled dataset (70/30 benign-to-malicious class balance), trains the Random Forest, evaluates it against held-out data, and serializes the result to `random_forest.pkl`.

Labels come from the profile category — benign profiles produce label `0`, attack profiles produce label `1`. The rule engine has no role in the labeling process and is never invoked during training.

### Positive Consequences

* The two ensemble paths are genuinely independent: the rule path expresses policy authors' explicit knowledge as weighted signals and conditions; the ML path expresses statistical patterns from domain-curated archetypes. When they agree, the agreement is meaningful.
* The ML path can detect multi-signal correlations the rule engine cannot express. A "low-and-slow probe" where every individual signal is moderate (0.25–0.45) but the combination is rare in benign traffic is exactly the kind of pattern Random Forest learns well and a linear weighted sum cannot.
* The 12 profiles are inspectable and modifiable. Future maintainers can read the profile definitions to understand what the model has been taught.
* The training process is fully reproducible. Running the script produces the same model (modulo the random seed) every time.
* The training data lives in code, not in opaque datasets. Modifications go through code review.

### Negative Consequences

* The model's behavior is bounded by the imagination of the profile designers. Attack patterns not represented in any profile are unlikely to be detected. Acceptable in the demo context; production would augment with real labeled data.
* The synthetic distributions are necessarily simplifications. Real malicious traffic is messier than any parameterized profile.
* The 16-feature vector and its column ordering must be kept synchronized between training and inference. Mitigated by defining the column ordering in a single shared module (`shared/naas_shared/ml_features.py`) imported by both the training script and the Risk Evaluator.

## Pros and Cons of the Options

### Parameterized distribution profiles with category-derived labels

* Good, because the ML path is genuinely independent of the rule path
* Good, because profile definitions are inspectable and version-controllable
* Good, because the training process is fast and reproducible
* Good, because the design encodes domain knowledge transparently
* Bad, because coverage is bounded by profile design
* Bad, because synthetic distributions are simpler than real attacker behavior

### Train on rule-engine output

* Good, because it produces a large labeled dataset trivially
* Bad, because the resulting ensemble is `0.6 × rules + 0.4 × rules_again` — the entanglement anti-pattern
* Bad, because it makes the ensemble's apparent disagreement-detection ability illusory
* Bad, because it would justify the ML path while delivering no real ML benefit — the worst outcome for a project that should demonstrate sound ML practice

### Train on real production data

* Good, because real data captures real attacker behavior
* Bad, because it does not exist for NAAS
* Bad, because, even if it existed, sourcing labeled IAM event data for a personal project would raise privacy and licensing concerns

### Generate training data with an LLM

* Good, because an LLM can produce a large volume of plausible-looking event records quickly
* Bad, because LLMs generate text that *sounds* statistically reasonable without producing data that *is* statistically reasonable — distributional accuracy is a known weakness
* Bad, because the model would be learning the LLM's hallucinated statistics, not real or domain-derived ones
* Bad, because the labeling problem is untouched: the LLM's "this is malicious" judgement is no more grounded than its "this person is named Alice" judgement
* Bad, because it externalizes the most important design decision (what makes traffic malicious?) to a non-deterministic black box

### Skip ML entirely

* Good, because it removes a whole class of complexity
* Bad, because the project's narrative includes hybrid rule/ML scoring; removing ML weakens the narrative
* Bad, because the rule engine's linear weighted sum cannot detect correlated multi-signal patterns, which is precisely the failure mode the ML path addresses

## More Information

The 16-feature vector is deliberately broader than the 4 continuous signals consumed by the rule engine's `signal_weights`. The ML path sees the full evaluation context — continuous signals plus booleans (impossible travel, known device, on-corporate-network, VPN-connected) plus derived time features (business hours, weekend) plus one-hot encoded protocol and employee-type. This breadth is what enables learning correlations the rule engine cannot express.

The 70/30 benign-to-malicious split intentionally over-represents the malicious class relative to a realistic IAM traffic distribution (which would be closer to 99/1 benign). Over-representation prevents the model from learning the trivial baseline of "always predict benign," which would achieve 99% accuracy on a realistic distribution while being useless. This is standard practice for imbalanced classification but worth recording explicitly.

If `random_forest.pkl` is missing at Risk Evaluator startup, the ML path is gracefully disabled — the model returns `0.0` for every event, and the ensemble blend reduces to the rule engine's score. This means the system remains operational during the brief window between scaffold completion and the first run of the bootstrap script.

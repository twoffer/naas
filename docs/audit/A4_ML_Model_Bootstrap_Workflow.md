# ML Model Bootstrap Workflow
## Design Reference for Spec 3 — Risk Evaluator (ML Scoring Path)

**Purpose:** Define the training data generation strategy, feature vector specification, model training and evaluation workflow, and bootstrap script design for the NAAS Random Forest classifier — resolving the "somebody needs to generate `random_forest.pkl`" gap identified in the A3 spec.

**Audience:** Claude Code agents implementing the ML scoring path in Spec 3, the technical-architect agent producing the Spec 3 implementation plan, and the project architect.

---

## 1. Overview

The NAAS Risk Evaluator uses a hybrid ensemble model: a rule-based scoring path (signal weights + boolean conditions) blended with an ML-based scoring path (Random Forest classifier). The A3 spec defines the ensemble integration point — `ml_model_predict(event_record)` returns a float 0.0–1.0 representing the probability that an event is malicious — but explicitly defers *how the model is generated* to this A4 spec.

### 1.1 The Cold Start Problem

A Random Forest model is a static artifact. It must be trained on labeled data before it can make predictions. NAAS operates on synthetic data (generated by the Persona Simulator or via API), so there is no production traffic to learn from. The model must be bootstrapped from synthetically generated training data that encodes IAM domain knowledge about what benign and malicious access patterns look like.

### 1.2 The Entanglement Anti-Pattern

A naive approach would train the ML model on labels derived from rule-based scoring output (i.e., "the rules said DENY, so label it malicious"). This creates a circular dependency: the ML path learns to approximate the rule path, and the ensemble degenerates into `0.6 × rules + 0.4 × rules_again`. The two scoring paths must derive their conclusions from **independent reasoning** — rules from explicit signal weights and boolean conditions defined by policy authors, ML from statistical patterns learned from labeled distribution profiles defined by IAM domain knowledge. This independence is what makes the ensemble valuable.

### 1.3 Design Principle: Where ML Adds Value

The rule-based path is a linear weighted sum — it cannot learn non-linear feature interactions. The ML path's primary value is detecting **correlated multi-signal patterns** that no single signal or condition would flag. For example, a "low and slow probe" where every signal is individually moderate (0.25–0.45 range) but the *combination* of slightly elevated IP risk + VPN + unknown device + off-network almost never appears in benign traffic. The rule engine scores this as middling; the Random Forest learns it's suspicious from the training data distributions.

### 1.4 Code Samples in This Document

**The code samples throughout this document are illustrative reference implementations**, not copy-paste production code. They establish the algorithms, data structures, and contracts that the implementing agent must follow, but the implementing agent is expected to:

- Adapt to actual project structure, imports, and conventions
- Apply proper error handling, type annotations, and logging
- Follow project code style (Black formatting, mypy compliance)
- Use the patterns as behavioral specifications, not literal implementations

## 2. Feature Vector Specification

The ML model consumes a **16-column feature vector** derived from the enriched event data. This is deliberately broader than the 4 continuous signals used by the rule-based signal weights path — the ML model has access to the full evaluation context (minus high-cardinality string fields), enabling it to learn correlations the rule engine cannot express.

### 2.1 Feature Table

| # | Feature Name | Type | Range | Source | Notes |
|---|-------------|------|-------|--------|-------|
| 1 | `ip_reputation_risk` | float | 0.0–1.0 | Signal normalizer (A3 §4.2) | Pre-normalized continuous signal |
| 2 | `normalization_risk` | float | 0.0–1.0 | Signal normalizer (A3 §4.3) | `1.0 - normalization_confidence` |
| 3 | `failed_login_risk` | float | 0.0–1.0 | Signal normalizer (A3 §4.4) | Normalized from `failed_logins_24h` |
| 4 | `login_recency_risk` | float | 0.0–1.0 | Signal normalizer (A3 §4.5) | Normalized from `days_since_last_login` |
| 5 | `impossible_travel` | int | 0 or 1 | `enriched_signals.impossible_travel` | Bool cast to int |
| 6 | `known_device` | int | 0 or 1 | `enriched_signals.device.known_device` | Bool cast to int |
| 7 | `on_corporate_network` | int | 0 or 1 | `enriched_signals.device.on_corporate_network` | Bool cast to int |
| 8 | `vpn_connected` | int | 0 or 1 | `enriched_signals.device.vpn_connected` | Bool cast to int |
| 9 | `is_business_hours` | int | 0 or 1 | Derived: `8 <= event.timestamp.hour <= 18` | Computed at feature extraction time |
| 10 | `is_weekend` | int | 0 or 1 | Derived: `event.timestamp.weekday() >= 5` | 0=Monday convention (ISO) |
| 11 | `protocol_oidc` | int | 0 or 1 | One-hot from `event.protocol` | Mutually exclusive with 12, 13 |
| 12 | `protocol_saml` | int | 0 or 1 | One-hot from `event.protocol` | Mutually exclusive with 11, 13 |
| 13 | `protocol_ldap` | int | 0 or 1 | One-hot from `event.protocol` | Mutually exclusive with 11, 12 |
| 14 | `employee_fte` | int | 0 or 1 | One-hot from `user.employee_type` | Mutually exclusive with 15, 16 |
| 15 | `employee_contractor` | int | 0 or 1 | One-hot from `user.employee_type` | Mutually exclusive with 14, 16 |
| 16 | `employee_vendor` | int | 0 or 1 | One-hot from `user.employee_type` | Mutually exclusive with 14, 15 |

### 2.2 Feature Ordering Contract

The feature vector must be assembled in exactly the order listed above (columns 1–16). The training script and the Risk Evaluator's runtime feature extraction must use the same column ordering. A mismatch will produce silently wrong predictions — the model will interpret one signal's values as another signal.

**Implementation requirement:** Define the feature column names as a constant list in `shared/naas_shared/ml_features.py` (or equivalent shared location) and import it in both the training script and the Risk Evaluator. Do not duplicate the list.

```python

```

### 2.3 Why These Features, Why Not Others

**Included:** Features that carry security-relevant signal and have low cardinality (≤ 3 categories for one-hot encoding) or are continuous/boolean.

**Excluded:**
- `user.department` — High cardinality, weak signal-to-noise ratio. The model would overfit to "Security department = safe."
- `user.groups` — Variable-length list, complex to encode, security-relevant subsets (admin groups) would need domain-specific feature engineering beyond MVP scope.
- `device.browser`, `device.os` — High cardinality strings. Useful features like `is_outdated_browser` would require engineering that's P2 scope.
- `signals.country`, `signals.city` — High cardinality (195+ countries). Geographic risk is already captured implicitly by `ip_reputation_risk`.
- `event.source`, `event.is_synthetic`, `event.is_historical` — These are metadata about how the event was generated, not security signals. Including them would teach the model "synthetic events are benign" which is a data leakage problem.

### 2.4 Runtime Feature Extraction

The Risk Evaluator must extract the 16-feature vector from each enriched event record before calling `model.predict_proba()`. This function lives in the Risk Evaluator service, not in the shared library.

```python
def extract_ml_features(event_record, normalized_signals: dict) -> list[float]:
    """
    Extract the 16-feature ML vector from an enriched event record.

    Args:
        event_record: The enriched event (with normalized_attributes,
                      enriched_signals, timestamp, protocol fields)
        normalized_signals: The dict of pre-normalized signal values
                           (ip_reputation_risk, normalization_risk, etc.)
                           as computed by the signal normalizer functions.

    Returns:
        list[float] of length 16, in ML_FEATURE_COLUMNS order.
    """
    signals = event_record.enriched_signals or {}
    device = signals.get("device", {})
    norm = event_record.normalized_attributes or {}

    protocol = event_record.protocol  # "oidc", "saml", or "ldap"
    emp_type = norm.get("employee_type", "unknown")

    return [
        # Continuous signals (pre-normalized 0.0–1.0)
        normalized_signals.get("ip_reputation_risk", 0.5),
        normalized_signals.get("normalization_risk", 0.5),
        normalized_signals.get("failed_login_risk", 0.0),
        normalized_signals.get("login_recency_risk", 0.5),
        # Boolean signals (cast to int)
        int(signals.get("impossible_travel", False)),
        int(device.get("known_device", False)),
        int(device.get("on_corporate_network", False)),
        int(device.get("vpn_connected", False)),
        # Derived time features
        int(8 <= event_record.timestamp.hour <= 18),
        int(event_record.timestamp.weekday() >= 5),
        # One-hot: protocol (mutually exclusive)
        int(protocol == "oidc"),
        int(protocol == "saml"),
        int(protocol == "ldap"),
        # One-hot: employee type (mutually exclusive)
        int(emp_type == "FTE"),
        int(emp_type == "contractor"),
        int(emp_type == "vendor"),
    ]
```

**Default values for missing data:** Continuous signals default to 0.5 (uncertain/neutral) rather than 0.0 (safe), except `failed_login_risk` which defaults to 0.0 (no failed logins is the safe assumption). Booleans default to `False`. If `employee_type` is `"unknown"`, all three one-hot columns are 0 — the model handles this as a learned pattern (no employee type assertion is itself a signal).

## 3. Training Data Generation

### 3.1 Strategy: Parameterized Distribution Profiles

Training data is generated synthetically by sampling from **distribution profiles** that encode IAM domain knowledge about what benign and malicious access patterns look like statistically. Each profile defines the mean and standard deviation for continuous features, and the probability of `True` for boolean features.

This approach is chosen over alternatives for specific reasons:
- **Not trained on rule-engine output:** Avoids the entanglement anti-pattern (§1.2).
- **Not generated by LLM:** An LLM has no special insight into realistic distributions of float signal values — it would hallucinate statistics with false confidence.
- **Not derived from external datasets:** Public cybersecurity datasets (LANL, etc.) don't map to NAAS's specific feature space without fragile ETL mappings.
- **Deterministic and reproducible:** A fixed random seed produces the exact same model every time. CI-friendly and debuggable.
- **Self-documenting:** The profile names and parameters *are* the threat model documentation. A portfolio reviewer reads `"compromised_insider"` with low `ip_reputation_risk` and immediately understands the design intent.

### 3.2 Profile Schema

Each profile is a named dictionary with the following structure:

```python
@dataclass
class DistributionProfile:
    """A named behavioral profile for synthetic training data generation."""
    name: str                                    # e.g., "credential_stuffing"
    label: int                                   # 0 = benign, 1 = malicious
    weight: float                                # sampling weight (proportion of category)
    continuous: dict[str, tuple[float, float]]   # feature_name → (mean, std_dev)
    boolean: dict[str, float]                    # feature_name → probability of True
    categorical: dict[str, dict[str, float]]     # group_name → {value: probability}
```

**Sampling rules:**
- **Continuous features:** Sampled from `N(mean, std_dev)`, clamped to [0.0, 1.0].
- **Boolean features:** Sampled from `Bernoulli(probability)`, cast to int (0/1).
- **Categorical features:** Sampled from a categorical distribution (one value selected per group). The probabilities within a group must sum to 1.0. The selected value is one-hot encoded into the corresponding columns.

### 3.5 Design Notes on Profile Overlap

The `road_warrior` (benign) and `compromised_account_remote` (malicious) profiles deliberately overlap in the `impossible_travel` and off-network dimensions. The distinguishing features are `known_device` (0.80 vs 0.05) and `ip_reputation_risk` (0.30 vs 0.75). The model must learn that *context* matters — impossible travel alone is not malicious. This is realistic IAM and demonstrates false-positive management to portfolio reviewers.

Similarly, `remote_worker` (benign) and `compromised_account_vpn` (malicious) overlap in VPN usage. The distinguishing features are `known_device` (0.85 vs 0.05) and `on_corporate_network` (0.10 vs 0.02, both low but the benign profile occasionally connects directly). These overlaps force the model to learn multi-signal correlations rather than single-feature thresholds.

### 3.6 Benign/Malicious Class Balance

The generated dataset should use a **70/30 benign-to-malicious split**. Real enterprise traffic is overwhelmingly legitimate (> 99% benign), but a 70/30 ratio gives the model enough malicious samples to learn attack patterns while still reflecting the baseline assumption that most traffic is benign. A 50/50 split would teach the model to over-predict malicious events.

The class balance ratio is configurable via a command-line argument (default: 0.7).

## 4. Bootstrap Training Script

### 4.1 Location and Invocation

The training script lives at `scripts/train_bootstrap_model.py` in the repository root. It is a standalone CLI script — not a running service, not a Docker container, not imported by any service at runtime.

```bash
# Default: 5000 samples, 70/30 split, random_state=42
python scripts/train_bootstrap_model.py

# Custom parameters
python scripts/train_bootstrap_model.py \
    --num-samples 10000 \
    --benign-ratio 0.7 \
    --random-state 42 \
    --output-model services/risk-evaluator/models/random_forest.pkl \
    --output-csv scripts/training_data.csv \
    --output-report scripts/training_report.txt
```

### 4.2 Script Responsibilities

The script performs these steps in order:

1. **Define distribution profiles** (benign and malicious, as specified in §3.3–3.4)
2. **Generate synthetic samples** by sampling from profiles according to their weights and the benign/malicious ratio
3. **Split** into 80% training / 20% test sets (stratified by label to preserve class balance)
4. **Train** a `RandomForestClassifier` with `n_estimators=100, random_state=<seed>`
5. **Evaluate** on the held-out test set, print precision/recall/F1/confusion matrix
6. **Serialize** the trained model via `joblib.dump()` to the output path
7. **Optionally save** the generated dataset to CSV for inspection
8. **Optionally save** the evaluation report to a text file

### 4.3 Sampling Algorithm

```python
def generate_training_data(
    benign_profiles: list[DistributionProfile],
    malicious_profiles: list[DistributionProfile],
    num_samples: int,
    benign_ratio: float,
    rng: np.random.Generator,
) -> tuple[np.ndarray, np.ndarray]:
    """
    Generate synthetic training data from distribution profiles.

    Returns:
        (features, labels) where features is (num_samples, 16) and labels is (num_samples,)
    """
    num_benign = int(num_samples * benign_ratio)
    num_malicious = num_samples - num_benign

    benign_samples = _sample_from_profiles(benign_profiles, num_benign, label=0, rng=rng)
    malicious_samples = _sample_from_profiles(malicious_profiles, num_malicious, label=1, rng=rng)

    all_features = np.vstack([benign_samples[0], malicious_samples[0]])
    all_labels = np.concatenate([benign_samples[1], malicious_samples[1]])

    # Shuffle
    shuffle_idx = rng.permutation(len(all_labels))
    return all_features[shuffle_idx], all_labels[shuffle_idx]


def _sample_from_profiles(
    profiles: list[DistributionProfile],
    num_samples: int,
    label: int,
    rng: np.random.Generator,
) -> tuple[np.ndarray, np.ndarray]:
    """
    Sample from a list of profiles according to their weights.
    """
    weights = np.array([p.weight for p in profiles])
    weights = weights / weights.sum()  # Normalize to sum to 1.0

    # Determine how many samples per profile
    profile_counts = rng.multinomial(num_samples, weights)

    all_features = []
    for profile, count in zip(profiles, profile_counts):
        features = _sample_single_profile(profile, count, rng)
        all_features.append(features)

    features = np.vstack(all_features)
    labels = np.full(num_samples, label)
    return features, labels


def _sample_single_profile(
    profile: DistributionProfile,
    num_samples: int,
    rng: np.random.Generator,
) -> np.ndarray:
    """
    Generate feature vectors for a single profile.

    Continuous features: N(mean, std), clamped to [0, 1]
    Boolean features: Bernoulli(p), cast to float (0.0 or 1.0)
    Categorical features: Categorical draw, one-hot encoded
    """
    features = np.zeros((num_samples, len(ML_FEATURE_COLUMNS)))

    for col_idx, col_name in enumerate(ML_FEATURE_COLUMNS):
        if col_name in profile.continuous:
            mean, std = profile.continuous[col_name]
            values = rng.normal(mean, std, num_samples)
            features[:, col_idx] = np.clip(values, 0.0, 1.0)

        elif col_name in profile.boolean:
            prob = profile.boolean[col_name]
            features[:, col_idx] = rng.binomial(1, prob, num_samples).astype(float)

    # Handle categorical features (mutually exclusive one-hot groups)
    for group_name, probabilities in profile.categorical.items():
        values = list(probabilities.keys())
        probs = list(probabilities.values())
        # Column name pattern: "{group}_{value}" e.g., "protocol_oidc"
        col_names = [f"{group_name}_{v}" for v in values]
        col_indices = [ML_FEATURE_COLUMNS.index(cn) for cn in col_names]

        choices = rng.choice(len(values), size=num_samples, p=probs)
        for sample_idx, choice in enumerate(choices):
            features[sample_idx, col_indices[choice]] = 1.0

    return features
```

**Critical implementation detail:** The categorical columns (protocol, employee_type) must be sampled as a single categorical draw, not as independent Bernoulli flips. Independent sampling could produce impossible combinations like `protocol_oidc=1, protocol_saml=1, protocol_ldap=1`. The code above handles this correctly via `rng.choice()`.

## 5. Risk Evaluator Integration

### 5.1 Model Loading

The Risk Evaluator loads the model file once at startup. If the file is missing, the ML scoring path is disabled and the ensemble falls back to 100% rule-based scoring.

```python
import joblib
from pathlib import Path

MODEL_PATH = Path("models/random_forest.pkl")

def load_ml_model():
    """
    Load the serialized Random Forest model at service startup.
    Returns None if model file is missing (ML path disabled).
    """
    if not MODEL_PATH.exists():
        logger.warning(
            "ML model not found at %s — ML scoring disabled, "
            "ensemble will use 100%% rule-based scoring",
            MODEL_PATH,
        )
        return None
    model = joblib.load(MODEL_PATH)
    logger.info("ML model loaded from %s", MODEL_PATH)
    return model
```

### 5.2 ML Scoring Function

```python
def ml_model_predict(model, feature_vector: list[float]) -> float:
    """
    Get malicious probability from the Random Forest model.

    Args:
        model: The loaded RandomForestClassifier (or None if unavailable)
        feature_vector: 16-element list in ML_FEATURE_COLUMNS order

    Returns:
        float 0.0–1.0 (probability of malicious), or 0.0 if model is None
    """
    if model is None:
        return 0.0  # ML path disabled — contributes nothing to ensemble

    features = np.array([feature_vector])
    proba = model.predict_proba(features)[0]

    # predict_proba returns [P(benign), P(malicious)]
    # Index 1 is the malicious probability
    return float(proba[1])
```

### 5.3 Ensemble Fallback Behavior

When the ML model is not available (`model is None`), the `ml_model_predict` function returns `0.0`. Combined with the ensemble formula `final = (rule × rule_weight) + (0.0 × ml_weight)`, the effect is that the rule-based score is *deflated* by the missing ML contribution. This is the conservative (safe) behavior — the system under-scores rather than over-scores when the ML path is missing, and the rule-based thresholds still apply.

**Alternative considered and rejected:** Dynamically adjusting the ensemble weights to `1.0 / 0.0` when the model is missing. This would silently change the scoring behavior in a way that's hard to reason about. The constant `0.0` approach is simpler and more predictable. If the operator wants pure rule-based scoring, they should set `ensemble.ml_weight: 0.0` in the policy YAML explicitly.

### 5.4 Model Hot-Reload (P2 — Not in MVP)

For MVP, changing the model requires restarting the Risk Evaluator service. A future enhancement could watch the model file for changes and reload without restart, but this is beyond MVP scope.

## 7. What This Spec Does NOT Cover

- **Online learning / continuous retraining.** The model is a static artifact. Automatic retraining from production data is a P2 concern (the "ML Training Service" in SYSTEM_ARCHITECTURE.md).
- **Hyperparameter tuning.** The default `n_estimators=100, max_depth=10` configuration is sufficient for the bootstrap model. Grid search / cross-validation is a P2 concern.
- **Model versioning.** The `.pkl` file is replaced in-place. Version tracking of model files is a P2 concern.
- **Jupyter notebook / exploratory analysis.** The AARE v1 foundation doc mentions an `ml_training/notebooks/` directory — this is not needed for MVP. The training script's evaluation output provides sufficient model quality feedback.
- **Dashboard visualization of ML internals.** Feature importances, decision boundaries, and model diagnostics are not displayed in the dashboard. The dashboard shows the `ml_based_score` float and contributing factors — it does not expose *why* the Random Forest arrived at that score. This is a deliberate scope boundary; explainable ML visualization is a P2 concern.
- **Model monitoring / drift detection.** Detecting when the model's predictions degrade relative to new data patterns is a production concern beyond portfolio scope.

## 8. Verifiable Success Criteria

The implementing agent (via Spec 3 and the bootstrap script) must satisfy these criteria:

### 8.1 Training Script

1. `python scripts/train_bootstrap_model.py` runs without error and produces `random_forest.pkl` at the specified output path.
2. The script accepts `--num-samples`, `--benign-ratio`, `--random-state`, `--output-model`, `--output-csv`, and `--output-report` CLI arguments with sensible defaults.
3. Running the script twice with the same `--random-state` produces a byte-identical `.pkl` file.
4. The generated dataset contains exactly `num_samples` rows with the expected benign/malicious ratio (±1 sample due to integer rounding).
5. The evaluation report shows precision, recall, and F1-score for both classes, a confusion matrix, and the top 10 feature importances.
6. All 12 distribution profiles (6 benign, 6 malicious) are implemented as specified in §3.3–3.4.
7. Categorical features (protocol, employee_type) are sampled as mutually exclusive categorical draws, not independent Bernoulli flips.

### 8.2 Risk Evaluator Integration

1. The Risk Evaluator loads `random_forest.pkl` at startup and logs a message confirming the load.
2. If `random_forest.pkl` is missing, the Risk Evaluator starts successfully with a warning log, and `ml_model_predict` returns `0.0` for all events.
3. The feature extraction function (`extract_ml_features`) produces a 16-element vector in the exact order defined by `ML_FEATURE_COLUMNS`.
4. The feature column list is imported from a shared location (`shared/naas_shared/ml_features.py`), not duplicated between the training script and the Risk Evaluator.
5. `model.predict_proba()` is called with a 2D array of shape `(1, 16)` and the result `[0][1]` (malicious probability) is returned as the `ml_score`.
6. The `ml_score` is included in the `risk_assessments.contributing_factors` JSONB for dashboard display.

### 8.3 Model Quality (Informational, Not Blocking)

With the default parameters (5000 samples, 70/30 split, random_state=42), the model should achieve:
- Overall accuracy ≥ 0.85
- Malicious recall ≥ 0.80 (catches at least 80% of attacks in the test set)
- Benign precision ≥ 0.85 (when it says "benign," it's right at least 85% of the time)

These thresholds are informational guidelines, not hard pass/fail criteria. If the model underperforms, the most likely cause is a profile misconfiguration (e.g., too much overlap between benign and malicious distributions), not a code bug.

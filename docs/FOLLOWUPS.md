## Pre-deployment security hardening

Demo-scope postures that are intentional for local development and explicitly out of scope until a non-local (shared/staging/production) deployment is on the table. Harden all of these before exposing the stack beyond localhost.

- **Keycloak demo client posture** — `infrastructure/keycloak/naas-realm-export.json`: `publicClient: true` + ROPC (`directAccessGrants: true`) + `sslRequired: "none"`. Before non-local deploy: switch to a confidential client with PKCE, disable ROPC, set `sslRequired` to `external`/`all`. _(Source: security review, chunk 4)_
- **LDAP plaintext passwords** — `infrastructure/openldap/bootstrap.ldif`: `userPassword: password123` is plaintext. Real directories must store hashed passwords (e.g. `{SSHA}`). _(Source: security review, chunk 4)_
- **Host port exposure** — `docker-compose.yml`: postgres `5432`, redis `6379`, keycloak `8080`, openldap `389`/`636` are bound to the host with dev credentials. For non-local hosts, bind to `127.0.0.1` or drop the host port mappings and rely on `naas-network`. _(Source: security review, chunk 5)_
- **Redis authentication** — `infrastructure/redis/redis.conf`: no `requirepass`/ACL. Add when promoted beyond local dev. _(Source: security review, chunk 3)_

## Service code-quality nits

Minor non-blocking quality items in service code. No lint gate enforces them; low value, deferred.

- **`HealthResponse.version` / app-version drift** — `shared/naas_shared/models.py` defaults `version` to a hardcoded `"2.0.0"` while each service's `FastAPI(version="2.0.0")` is an independent literal; the health endpoint reports the shared default regardless of the app's declared version, so the two will silently diverge. Derive both from a single per-service constant (or pass the app version into `HealthResponse`). _(Source: post-Spec-0/1 review)_
- **Cross-service `swagger_ui_oauth2_redirect_url` alignment** — `services/identity-normalization/app/main.py` sets `swagger_ui_oauth2_redirect_url=None` (now with an explanatory comment) while `services/event-ingestion/app/main.py` omits it. Neither service has OAuth2-protected endpoints, so both are correct; aligning them for uniformity would touch event-ingestion and is deferred. _(Source: Spec 2 remediation triage; security review chunk 1)_
- **Raw attribute value logged at WARNING** — `services/identity-normalization/app/normalization_values.py` (`normalize_department`/`normalize_employee_type` unmapped-value path): logs `raw_value=<value>` (the raw department/employee_type string) at WARNING. Low sensitivity (not email/name/token) and pre-existing, but worth redacting/bounding in a future cleanup. Note this warning path is also entirely untested. _(Source: Spec 2 remediation security review, LOW; Spec 2 end-to-end review)_
- **Carry department `was_mapped` end-to-end instead of round-trip re-derivation** — `services/identity-normalization/app/service.py` (`_was_department_mapped`): the adapters run `normalize_department()` and discard the `was_mapped` flag; the service re-derives it by checking that the normalized string round-trips through `DEPARTMENT_CANONICAL`. This only works because every canonical value's lowercase is itself a key — a property now pinned by a guard test (`test_normalization_values.py::TestWasDepartmentMappedRoundTrip`), so violations fail the suite rather than silently corrupting confidence scoring. The clean fix — have the department FieldRule carry the `(str, was_mapped)` tuple from `extract()` through to resolution and delete `_was_department_mapped` — changes the adapter output contract and ripples through `_merge_ldap_attrs`, resolution, the demo, and many tests; do it as a deliberate refactor. _(Source: Spec 2 end-to-end review)_
- **Empty-string scalars become resolution sources** — `services/identity-normalization/app/service.py` (`_build_attribute_sources`): the docstring promises "non-None, non-empty values" but the scalar loop checks only `is not None`, so an empty-string `display_name`/`primary_email` claim becomes a contributing source (and can win resolution). Decide the intended semantics (probably skip empty strings like groups skips empty lists), fix the code or the docstring, and pin with a test. _(Source: Spec 2 end-to-end review)_
- **LDAP enrichment config-evolution edges** — `services/identity-normalization/app/adapters/ldap.py`: three defended-in-depth edges that only become reachable if config stops being process-fixed: (a) `OPT_NETWORK_TIMEOUT`/`OPT_TIMEOUT` are applied at connection creation only, so pooled connections would retain a stale `timeout_ms` under hot-reload; (b) the positive-cache key omits `enrich_attributes`, so two processes sharing Redis with divergent attrlist configs could replay a restricted entry to a full-attrlist caller (bounded by the TTL); (c) the `enrich_attributes` attrlist build subscripts `UNIFIED_TO_LDAP[f]` outside the LDAP try block — an unmapped field would surface as a service-level `ldap_search_error` skip rather than a classified error (unreachable: startup validation rejects unmapped fields). Address if hot-reload or per-process config divergence ever lands. _(Source: Spec 2 remediation security review, LOW ×3)_
- **Residual pipeline vocabulary in production docstrings** — `services/identity-normalization/app/service.py:275` ("per chunk-5 contract"), `app/main.py:7` ("(chunk 6)"), `app/main.py:182` ("In Chunk 1"), `app/adapters/oidc.py:37` ("(chunk 6)"): build-provenance wording survives in four production docstrings (the test suite was already scrubbed; sites touched by the Spec 2 remediation were reworded in passing). ## Forward-looking design items

Decisions deferred to the spec that first needs them.

- **Keycloak group-name binding (plain vs slash)** — `infrastructure/keycloak/naas-realm-export.json` uses plain group names (`engineering`/`product`/`security`); SPEC_0 §6.4 acceptance does not assert group-membership binding via the OIDC `groups` claim. Resolve the plain-vs-slash question in the **first downstream spec that consumes the OIDC `groups` claim** (identity-normalization / risk-evaluator). Note: this is **not** Spec 1 (event ingestion → Postgres/Redis), so it does not block the immediate next spec. _(Source: security review, chunk 4)_
- **Broader RFC-4514 DN conformance + directory-sourced-groups live assertion** — `services/identity-normalization/app/adapters/ldap.py` `_reduce_dn_to_group_name` uses `ldap.dn.str2dn` (handles escaped commas) with a regex fallback. Remaining RFC-4514 edge cases (hex `\NN` escapes, multi-valued/`+`-joined RDNs) are still untested. The original premise ("the seeded directory has no `memberOf`") is obsolete: the memberOf overlay + `groupOfNames` entries now give seeded users real back-links, and `tests/integration/test_identity_normalization_live.py` exercises enrichment live — but its group assertion is satisfiable by the event's own claims (alice's event already carries `["engineering", "vpn-users"]`), so zero directory contribution would still pass. Residual work: RFC-4514 edge-case units, plus a live assertion that a group present **only** in the directory reaches the resolved `groups`. _(Source: Spec 2 remediation triage; security review chunk 2/4; Spec 2 end-to-end review)_
- **Stream-consumer redelivery & dead-letter policy (failed messages are currently never retried)** — `services/identity-normalization/app/consumer.py`: the loop reads only `{stream: ">"}` (new messages); there is no `XAUTOCLAIM`/`XCLAIM` and no startup read of `"0"`, and Redis Streams never auto-redeliver pending entries — so ANY un-ACKed message (poison message or transient normalize/write/publish failure) sits in the consumer group's PEL forever and is never reprocessed. This contradicts SPEC_2 §5.1 and the consumer's own docstring ("redelivered by Redis after the visibility timeout" — Redis Streams have no such mechanism; fix the docstring with the policy). The spec's own exemplary loop shares the gap. Decide a deliberate policy — claim-and-retry with a retry budget (`XAUTOCLAIM` on an interval), then dead-letter stream vs. ACK-and-drop for poison messages — via a short ADR; applies to all current and future stream consumers. _(Source: Spec 2 remediation integration validation, LOW; Spec 2 end-to-end review, MEDIUM)_
- **Publish-replay affordance for the ingestion dual-write** — Spec 1 §5.5 justifies catch-and-log on a failed `login_events` publish because the committed row "is replayable", but nothing marks rows as published vs. unpublished: replay requires correlating error logs by hand, and a crash in the window between commit and XADD leaves no log at all. Relatedly, the stream payload's `created_at` (app clock) differs from the row's DB-default `created_at`. Decide a deliberate mechanism (outbox-style published marker, periodic reconciliation sweep, or an explicit "logs-only, no replay" posture) when replay becomes real — likely alongside the dead-letter policy above. _(Source: post-Spec-0/1 review)_
- **Bulk batch-size bound placement** — the 1–5000 bulk bound is enforced only at the transport edge (`Body(min_length=1, max_length=5000)` in `services/event-ingestion/app/routes.py`); `IngestionService.ingest_many` accepts any-length list, so a future non-HTTP caller could attempt an unbounded single-transaction batch. Decide one authority — document the bound as a transport concern, or add a domain-level guard (don't duplicate both). _(Source: post-Spec-0/1 review)_
- **Persist the unmapped-value penalty on `SingleSourceResolution`** — `shared/naas_shared/models.py` / `services/identity-normalization/app/resolution.py`: only `PriorityResolution` carries `penalty_applied`; when the −0.2 normalization-failure penalty hits a single-source attribute (demo Scene 4's `Sorcery` department) the persisted detail records nothing — the penalty is visible only in the depressed confidence. Consumers (the demo's verification/rendering, future dashboards) must infer it relatively. Same nature as the `list_merge` `sources` addition: a small additive provenance field, to be bundled into the next shared-models revision. _(Source: demo-review remediation triage)_
